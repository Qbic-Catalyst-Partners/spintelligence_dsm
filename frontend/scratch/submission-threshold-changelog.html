Submission Threshold Rework

Every change made to the Submission Threshold ticketing flow in this session — who it now assigns to, how occurrences are judged, the escalation path, and the data-recording bugs found and fixed along the way.

01The flow, end to end

Submission Threshold used to assign a missed-occurrence ticket to L1 and wait for a manual click before it ever reached L2. It now goes straight to L2, and escalates itself correctly from there.

1

Admin assigns L2 user(s) to a screen

Submission Threshold's "Assigned to" field now lists L2 users only. Each rule row carries its own Department → Sub-Department → Notebook Type, so one save can cover several unrelated notebooks at once.

2

Occurrence is judged against the screen, not a person

Once a full calendar day has completed, the worker counts every submission to that notebook — by anyone: an L1, an L2, an admin. If the count meets the configured frequency, nothing happens.

midnight-to-midnight windows15-min check interval
3

Short → one ticket, straight to L2

If the count falls short, a single SUBMISSION_FREQUENCY ticket is raised with tat_current_level = 'L2'. L1 has no visibility into it at all — not via the approval array, not via "Owned Tickets."

no L1 stage
4

L2 fixes it → escalates to their own L3

Whichever assigned L2 clicks Fix & Submit, the ticket resolves the next approver from that person's real reporting chain — not a fixed manager picked at ticket-creation time.

5

L3 approves or rejects

Approve closes the ticket. Reject reopens it to L2 — not L1, which is what the generic reject handler used to assume for every ticket type.

02Backend changes

Four files, each carrying a distinct piece of the new routing logic.

routes/operatorTickets.routes.js
  • checkSubmissionFrequencyMissed() rewritten: creates the ticket at L2 (approval_l2_user_ids), leaves approval_l1_user_ids and user_id empty so no L1 can see it.
  • Occurrence count changed from "did a tracked user submit" to "did anyone submit" — total submissions to the screen, unscoped by submitter.
  • Live sync: if the config's assigned L2 list changes while a ticket is still open, the ticket's approver array updates on the next check — old tickets don't freeze at whoever was assigned when they were raised.
  • PUT /submit/:id ("Fix & Submit") no longer hardcodes the next level as L2 — it escalates to whatever sits above the ticket's current level, and resolves that approver from whoever is actually clicking submit, not a fixed ticket owner.
  • Added the authorization check this endpoint never had: only the ticket's owner, its current-level approvers, an active delegate, or an admin can submit it.
  • Unique index swapped: one ticket per config (operator_tickets_subfreq_missed_open_config_uq), replacing the old per-user index.
routes/supervisorTickets.routes.js
  • Reject handler no longer hardcodes tat_current_level = 'L1'. A ticket with no L1 stage reopens to L2 instead; every other ticket type is unaffected.
routes/submittedNotebooks.routes.js
  • notebook_submission_id now includes department + sub-department, not just notebook name + entry id — the fix for the cross-screen collision described in §05.
connection.js
  • Self-healing column check for tracked_l1_user_ids on screen_submission_frequency, guarded on the table existing. Runs on every server start — nothing to apply by hand.

03Frontend changes

views/thresholds/SubmissionThreshold.js
  • "Assigned to" now lists L2 users, multi-select — the dropdown that already existed in the file (built, never wired up) is now in use.
  • Sub-Department and Notebook Type moved from one shared top-of-form selector to per rule row — clicking + adds a row that can target a different notebook entirely, each with its own frequency, days, criticality, and L2 assignees.
  • "Existing Thresholds" column header and validation copy updated from L1 to L2 throughout.
  • Preview-before-save dialog now lists each row's own Sub-Department › Notebook and frequency, instead of one shared summary line.
apis/submissionFrequencyApi.js
  • Fixed a misdiagnosis bug: error.request is set on any completed request, response or not — the check only claims "Network Error: unable to reach…" now when error.response is genuinely absent, instead of mislabeling an expired-token 401 as a connectivity failure.

04Recording bugs found across departments

Occurrence counting only works if what gets recorded matches, character for character, what Submission Threshold expects. An audit across every department's data-entry screens turned up four places where it didn't.

DepartmentScreenWhat was wrongStatus
Blow Room BR Waste Study Entry Type 1/2/3 All three study types recorded under one generic name — thresholds set for a specific type never saw its submissions. fixed
Carding WheelChange Never called the recording function at all — invisible to every threshold, regardless of naming. fixed
Draw Frame Wheel Change (7 sub-types) All 7 recorded as generic "Wheel Change" instead of their specific Breaker/Finisher type names. fixed
Spinning Wheel Change Type 1/2/3 Same pattern — all three collapsed into one generic name. fixed
Wrapping Carding / Drawing / Simplex None of the three ever reached submitted_notebooks — recording wasn't wired in at all. fixed
Mixing, Comber, Simplex, Autoconer all screens Audited — every notebook name already matches exactly. already correct

One fix had to be reverted and redone. The first pass at the Draw Frame fix also deleted unrelated machine-dropdown fallback logic for Cots Data Entry and added a page reload on save-close — neither requested. That file was reverted to its original state and only the wheel-change naming fix was reapplied, as a clean 25-line addition.

05Data repair: the Nati Data Entry collision

Carding and Comber both have a screen called "Nati Data Entry," both minting entry IDs with the same NAT- prefix from independent counters. Before the fix above, notebook_submission_id was built from notebook name + entry ID only — no department. When Comber's counter reached NAT-0007, the same number Carding had already used weeks earlier, the newer save silently overwrote the older row's payload instead of creating its own.

✓

Repaired directly in the database, in one transaction: two new, correctly-scoped rows created for the real Comber submissions (right department, right timestamp, real payload), and the two original Carding rows restored to their correct metadata with a transparent data-loss marker in place of the payload that couldn't be recovered.

Going forward this can't recur — notebook_submission_id now includes department and sub-department.
